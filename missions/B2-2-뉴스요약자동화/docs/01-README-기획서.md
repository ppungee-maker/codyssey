# README / 기획서 — 뉴스 요약 자동화 워크플로우

필수 산출물 ③. 팀 역할, 주제 필터링 기준과 선택 이유, 에러 처리 정책과 선택 이유를 기록한다.

## 팀 역할 / 개인별 작업 요약

이 예시답안은 1인 + AI 페어(코디세이 QA 자동화 리포 소유자, Claude Code 세션)로 진행했다.

| 역할 | 담당 | 작업 |
|---|---|---|
| 워크플로우 설계 | 형님 + Claude | RSS→필터→요약→저장 파이프라인 구조 설계, Make 시나리오 클릭 실행 |
| 프롬프트 설계·검증 | Claude | 요약 프롬프트 초안 작성, `naeto chat`으로 실제 기사에 대해 사전 검증 |
| Notion 데이터베이스 | 형님 | 속성 4개 생성, Make 연동 |
| 문서화 | Claude | 실행가이드·작업로그·모범답안 작성 |

## 주제 필터링 기준

**기준**: RSS 항목의 `title`에 키워드 `AI`가 포함되는지 여부(대소문자 무관, `Contains` 필터).

**선택 이유**:
- 미션 예시가 "사전에 정의된 주제(예: AI)"를 명시적으로 들었기 때문에 그대로 채택.
- 제목만 검사하는 이유: RSS의 `description`은 요약 앞부분만 잘려서 오는 경우가 많아
  키워드가 본문 중간에 있으면 놓칠 수 있다. 반면 기술 뉴스 제목은 핵심 기술명(AI,
  모델명 등)을 앞에 명시하는 경향이 강해 제목 매칭만으로도 재현율이 충분하다고 판단.
- 태그 목록을 여러 개(`AI`, `LLM`, `머신러닝` 등)로 확장하지 않고 단일 키워드로 시작한
  이유: 요구사항이 "1건을 선택"이라 필터를 넓게 잡을 필요가 없었고, 필터가 너무 넓으면
  Make 무료 플랜의 월간 오퍼레이션 한도를 불필요하게 소모하기 때문.

## 에러 처리 정책

**정책**: AI 요약 HTTP 호출 실패 시 **1분 간격으로 최대 2회 재시도**, 그래도 실패하면
해당 기사를 "실패" 경로로 보내 원문 정보 + 에러 메시지를 별도 기록하고 파이프라인은
계속 다음 실행으로 진행(사람 개입 없이 자동 종료).

**선택 이유**:
- 재시도 2회 상한은 미션 요구사항에 명시된 값을 그대로 따름 — 상한이 없으면 API
  장애 시 무한 재시도로 비용이 새거나 Make 오퍼레이션을 다 소모할 위험이 있음.
- 1분 간격을 둔 이유: LLM API의 일시적 429(rate limit)·5xx 오류는 대개 수십초~1분
  안에 회복되는 경우가 많아, 너무 촘촘한 재시도보다 살짝 간격을 두는 쪽이 회복 확률이
  높다고 판단(경험적 근거 — B1-3에서 같은 패턴을 15분 간격으로 썼던 것보다 훨씬
  짧게 잡은 이유는, 이건 사람이 나중에 확인하는 배치가 아니라 매일 도는 짧은
  파이프라인이라 다음 스케줄까지 기다리게 하고 싶지 않았기 때문).
- 실패를 조용히 삼키지 않고 별도로 기록한 이유: "사람 개입 없이 자동 완료"는
  필수지만, 그게 "실패를 아무도 모르게 묻어버린다"를 의미하진 않는다고 판단 — 나중에
  실패 로그를 보고 원인을 파악할 수 있어야 한다.

## 중복 방지 정책

원문 링크(`link`)를 dedup 키로 사용 — 같은 기사를 다시 처리하기 전에 Notion에서
동일 링크를 가진 페이지가 있는지 먼저 조회하고, 있으면 스킵한다. 링크는 RSS 피드
내에서 사실상 유일한 식별자이자 사람이 봐도 무슨 기사인지 바로 알 수 있어 GUID
해시보다 디버깅하기 쉽다고 판단해 채택.

## 요약 호출 원칙

기사 1건당 요약 API 호출은 1회가 원칙(재시도 제외) — Router로 이미 "신규 기사인지"를
먼저 걸러낸 뒤에만 요약 단계로 보내기 때문에, 같은 기사에 대해 요약을 두 번 부르는
경로 자체가 없다.
